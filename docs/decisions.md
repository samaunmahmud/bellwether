# Decisions and assumptions

Choices made where the requirements were open. Each one can be revisited; the code comment or test that depends on it points back here by ID.

## Farm data model (FR-2)

| ID  | Assumption                                                                                                                                                             | Why                                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| A1  | A **housed** group's forecast uses the **farm postcode**, even if it still has a current field.                                                                        | Sheds are usually at the farmstead, not out in the field.                                               |
| A2  | A group's starting field is recorded as its **first movement**, dated today.                                                                                           | The movement history then always explains where the group is.                                           |
| A3  | A **backdated** move (earlier than the latest recorded move) is kept in the history but does not change the current field. Moves dated in the **future** are rejected. | Lets farmers fill in history without moving the group by mistake; planned moves are not real moves yet. |
| A4  | Map pins must fall inside an approximate UK bounding box (lat 49.8–60.9, long −8.7–1.8).                                                                               | Catches typos and swapped latitude/longitude. Bellwether is UK-only.                                    |
| A5  | "Today" always means the **UK date** (Europe/London), not the server's or UTC date.                                                                                    | Around midnight in summer the UTC date is a day behind.                                                 |
| A6  | Dairy cows and beef cattle get dairy/beef filled in automatically; calves can be either and may be left blank.                                                         | Avoids asking the same thing twice.                                                                     |
| A7  | ~~The old pet `Animal`/`LogEntry` store stays in memory~~ Superseded by A45: pets and logs are stored in Postgres.                                                     | Avoids migrating the pet model twice.                                                                   |
| A8  | Prisma is pinned to the stable **7.10.1**. npm's `latest` tag currently points at an 8.0 release candidate.                                                            | Release candidates can change without notice.                                                           |

## Users, sign-in and farm scoping (FR-8.1, FR-8.4)

| ID  | Assumption                                                                                                                                                                                                    | Why                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| A9  | **Email + password**, built in, rather than a managed auth provider. Passwords are hashed with Node's built-in **scrypt** and a random salt per user.                                                         | No third-party account or cost, works offline and in tests, and needs no new dependency. Swappable later behind `AuthService`. |
| A10 | Sessions are random 256-bit tokens in an **httpOnly, SameSite=Lax** cookie (also `Secure` in production). Only a SHA-256 hash of the token is stored. Sessions last 30 days; logging out deletes the session. | Revocable (unlike a JWT), not readable by page scripts, and not sent on cross-site POSTs.                                      |
| A11 | Passwords must be **10–128 characters**, with no rules about symbols or digits. Heuristic, TODO(verify source) against current UK guidance.                                                                   | Length matters more than complexity rules; the upper limit stops very long inputs from tying up the hasher.                    |
| A12 | Emails are trimmed and lower-cased, and must be unique. Sign-up says when an email is already registered; login failures always say "Email or password is incorrect".                                         | Clear sign-up for farmers; login doesn't reveal which half was wrong.                                                          |
| A13 | Whoever creates a farm becomes its **Owner**. The membership table already has a `role` column, but Worker/Viewer permissions arrive with FR-8.2 (P2).                                                        | FR-8.2 is P2; the schema won't need to change for it.                                                                          |
| A14 | Asking for another farm's data returns **not found** (or `null`), never "forbidden".                                                                                                                          | Doesn't reveal that the record exists.                                                                                         |
| A15 | The **postcode forecast stays public** because it reads no user data. **Pet animals and logs now need a login** and are scoped to their owner, until FR-2.6 moves them to a household profile.                | FR-8.4 asks for every query and mutation that touches user data to be scoped.                                                  |
| A16 | Deferred, not in P1: login rate limiting, email verification, password reset.                                                                                                                                 | Not in the P1 requirements. They are listed here so they aren't forgotten before a real launch.                                |
| A17 | The farm setup screens (farms, fields, groups, moves) are built in step 2, alongside the login screens.                                                                                                       | Both need the signed-in frontend, and the v2 definition of done needs farmers to set up their farm.                            |

## Risk engine upgrades (FR-3.0 to FR-3.4)

| ID  | Assumption                                                                                                                                                                                                                                                                                                           | Why                                                                                      |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| A18 | Weather extras (hourly data, wind, ET0, soil temperature) and group details are **optional** inputs. Every module still works without them, and the original modules behave exactly as before when they are missing.                                                                                                 | FR-3.0 requires the existing tests to pass unchanged.                                    |
| A19 | Adding a module to the registry **does** change one existing assertion: the registry test that lists the farm modules. That list was updated for lamb chill and fluke; no other existing test changed.                                                                                                               | Unavoidable: the test hard-codes the list.                                               |
| A20 | **Hourly heat stress** rounds each hour's THI to one decimal place before comparing with the bands, and sets the level from the day's peak.                                                                                                                                                                          | The reason shows rounded values, so "72.0" must count as at or above 72.                 |
| A21 | **Blowfly:** a flock with **no shearing date** is treated as unshorn and the reason says so. "Not shorn this season" is covered by the 42-day rule, because last season's shearing is always more than 42 days ago.                                                                                                  | Conservative, and it nudges farmers to record shearing.                                  |
| A22 | **Lamb chill** uses daily mean temperature, daily mean 10 m wind and daily rain. Lambs count as newborn until 3 days after the last lambing date. Days outside that window are Low ("Outside the lambing period"). Missing wind data counts as calm, and the reason says so.                                         | Matches published daily use of the index; first 72 hours is when lambs are most at risk. |
| A23 | **Liver fluke**: R and P in inches as in the original; rain day = 0.2 mm or more; months capped at 100 (50 for May and October); May–October only; Fox et al.'s 10 °C rule **not** applied; only **complete** months count. The season shown is this year's from June (once May is complete), otherwise last year's. | Follows the operational Met Éireann version, so its bands apply.                         |
| A24 | Fluke's past weather comes from the **Open-Meteo archive**, requested up to the last Sunday that is at least 5 days ago and cached for a week. So the season value refreshes weekly, as FR-3.3 asks. If the archive is down, fluke is simply left out and the other risks still show.                                | The archive is ~5 days behind; the forecast API's `past_days` only goes back 92 days.    |
| A25 | The **postcode-only farm forecast** (no group) leaves out lamb chill and fluke, because they need lambing dates or past weather.                                                                                                                                                                                     | Showing them without context would mislead.                                              |

## Records (FR-6.1 to FR-6.4, FR-6.6)

| ID  | Assumption                                                                                                                                                                                                                                                                                                      | Why                                                                                                                  |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| A26 | A treatment needs a date, product name, number of animals treated (1 to the group's head count), who gave it and a **meat** withdrawal period (0 allowed). Batch, quantity, reason and **milk** withdrawal are optional; no milk period means "not applicable". Quantity is free text and is never interpreted. | Matches what an audit asks for, without Bellwether ever handling doses.                                              |
| A27 | "Withdrawal ends" = treatment date + days: the first day the animals are out. The group is "In withdrawal" from the treatment date until the day before, using the UK date. Periods above 1000 days are rejected as typos.                                                                                      | FR-6.2 acceptance: treated 1 June + 28 days → ends 29 June, flagged up to 28 June.                                   |
| A28 | ~~Treatments and checks cannot be edited or deleted yet.~~ Superseded by A49–A52.                                                                                                                                                                                                                               | FR-6.5 (P2) says records are never hard-deleted and edits keep history; until then, no destructive operations exist. |
| A29 | The CSV is built in the browser from the same scoped GraphQL query as the printable table, so it can only contain the user's own farm. Cells starting with `=`, `+`, `-` or `@` are prefixed with `'` so typed-in text can't run as a spreadsheet formula. The default period is 1 January this year to today.  | No extra endpoint to secure; safe to open in Excel.                                                                  |
| A30 | Checks use a short list of general husbandry checks per species, plus "Other", and a free-text "What you found".                                                                                                                                                                                                | FR-6.6 example ("Flock inspected, 2 struck ewes found"), and no veterinary advice.                                   |
| A31 | Pets keep the old simple log until FR-2.6 moves them to a household profile; livestock groups use the new checks.                                                                                                                                                                                               | FR-6.6 replaces the old log for farms; FR-2.6 is P2.                                                                 |

## Briefing, tasks and email (FR-4.1 to FR-4.5, FR-5.1, FR-5.2, FR-5.5)

| ID  | Assumption                                                                                                                                                                                                                                                                                                                                                                                                                      | Why                                                                     |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| A32 | Suggested checks live on each risk module (`checks` at the top of its file), so adding a risk still needs only one new file. A test fails if any check mentions "dose", "mg" or "ml/kg".                                                                                                                                                                                                                                        | FR-5.1 asks for each module's wording in one place; hard rule 2.        |
| A33 | A briefing item's level is the **highest** level in the next 7 days (today to today + 6). Its reason is from the first day at that level, and its checks are that level's checks.                                                                                                                                                                                                                                               | One clear headline per risk, with the days listed.                      |
| A34 | "**New**" compares with **yesterday's stored run** only: High today and not High (or not flagged) yesterday. With no run yesterday, nothing is New.                                                                                                                                                                                                                                                                             | FR-4.4 acceptance; avoids marking everything New on a farm's first day. |
| A35 | One briefing is **stored per farm per UK day**. The page serves it all day; "Refresh" rebuilds it. A farm's first visit of the day builds it if the job hasn't yet. If the weather can't be fetched, the latest stored briefing is shown with its date and time and a clear notice.                                                                                                                                             | FR-4.5 (fast loads, comparable runs) and the reliability requirement.   |
| A36 | **Overdue tasks** are read live at the top of the briefing, not stored in the run, so ticking one off shows straight away.                                                                                                                                                                                                                                                                                                      | FR-5.5.                                                                 |
| A37 | One-tap tasks use the check as the title, are due on the first affected day (or today if that has passed), and belong to the group. Tasks can be marked done or not done; editing, deleting, recurring and assigning are P2.                                                                                                                                                                                                    | FR-5.2 vs FR-5.3/5.4.                                                   |
| A38 | **Email**: the job runs every 5 minutes (configurable). Each member gets at most one email per farm per day, at or after their chosen UK time (default 06:00). The day is claimed in the database before sending, so several servers can't double-send; if sending then fails, that day's email is lost and logged. A day counts as worth emailing if any risk is flagged **or** a task is overdue, unless "always send" is on. | FR-4.3; at-most-once is safer than duplicates.                          |
| A39 | A quiet day is also claimed, so it isn't re-checked every 5 minutes. If something becomes flagged later that day (e.g. after a refresh), no second email goes out.                                                                                                                                                                                                                                                              | Simple and predictable; the page is always current.                     |
| A40 | With no `SMTP_URL`, emails are logged (subject only, never the address) instead of sent. Dev uses Mailpit from Docker Compose on ports 1125/8125, so it can't clash with another project's mail catcher.                                                                                                                                                                                                                        | Local mail catcher (FR-4.3); privacy: no addresses in logs.             |
| A41 | **react-router v6** is kept for now. `npm audit` reports two moderate advisories: an open-redirect bypass via a backslash in `navigate` (the login page's `safeNext` already rejects `/\`) and an SSR issue (Bellwether doesn't use SSR). The fix is a breaking upgrade to v7.                                                                                                                                                  | Mitigated; a major upgrade belongs in its own step.                     |

## Working in the field (FR-10.1)

| ID  | Assumption                                                                                                                                                                                                                                                                                                                     | Why                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| A42 | Every button, input, select and toggle row is at least **48px** tall; checkboxes are 24px. Form fields use 17px text (16px or more stops phones zooming in). The base font is 17px, and secondary text is darker than usual for reading in daylight. A stylesheet test guards these rules, because jsdom can't measure layout. | FR-10.1: large tap targets, readable outdoors.                                                                                                    |
| A43 | Below 600px wide, forms collapse to one column and submit buttons go full width; a briefing check stays on one row with its "Add task" button on the right, within thumb reach. Affected days are shown as ranges ("Fri 16–Thu 22 Oct: High").                                                                                 | Checked with real 390px screenshots of the briefing, treatment form and farm page: a full-width button per check made the briefing ~3,400px long. |
| A44 | "New", "In withdrawal" and "Overdue" are always shown in words with a border, never by colour alone, in both light and dark themes.                                                                                                                                                                                            | Accessibility and glare.                                                                                                                          |

## Pets (FR-2.6)

| ID  | Assumption                                                                                                                                                                                                                                                                                                                                  | Why                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| A45 | Pets and their logs are stored in Postgres (`Pet`, `PetLogEntry`), still owned by one user. A shared household (several people looking after the same pets) is left for later.                                                                                                                                                              | Pets were lost on every restart. Ownership already worked per user (A15), so only storage changed.                       |
| A46 | Each pet can have a **home postcode** and a **"walks in long grass or woodland"** setting. Its page shows its own 14-day forecast, filtered to its species (tick and heatstroke for dogs, tick for cats). With no postcode there is no forecast, and the page says how to add one. The postcode is checked against postcodes.io when saved. | Turns the log page into a personal forecast, and an unknown postcode is caught when it's typed, not later.               |
| A47 | The pets page only adds **dogs and cats**. Existing "farm" animals from v1 still show, but livestock is added under My farms. Species can't be changed after adding.                                                                                                                                                                        | Farms, fields and groups replaced the old herd entries (FR-2). Changing species would make the log's history misleading. |
| A48 | Deleting a pet deletes its log too, after a confirmation. Log entries can be edited or deleted. Unlike livestock records (FR-6.5), pet logs are the owner's private notes, not audit records.                                                                                                                                               | Owners need to fix typos and remove pets they no longer have.                                                            |

## Corrections with history (FR-6.5)

| ID  | Assumption                                                                                                                                                                                                                                                          | Why                                                                                                     |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| A49 | Treatments and checks can be **corrected** or **voided**, never deleted. Every correction or void needs a reason and saves a revision: who (their email at the time), when, why, and each changed field's old and new value. Revisions can't be changed or deleted. | An audit trail needs to show what a record used to say and why it changed.                              |
| A50 | A **voided** treatment stays in the group's list and in the audit export (struck through, with "Voided: reason" in a Status column), but no longer counts for withdrawal. A voided record can't be corrected or voided again.                                       | Removing it from the export would hide the change; counting it would keep a wrongly entered withdrawal. |
| A51 | A correction is checked like a new record (dates not in the future, 1 to head count animals, 0–1000 withdrawal days). A correction that changes nothing is rejected. A record can't be moved to another group: void it and record it again.                         | Keeps the rules in one place, and a group's history is never rewritten silently.                        |
| A52 | In a correction, `null` clears an optional field (batch, quantity, reason, milk withdrawal, note) and is ignored for a required one.                                                                                                                                | GraphQL inputs can't make a field optional and non-null at the same time.                               |

## Tasks (FR-5.3)

| ID  | Assumption                                                                                                                                                                                                                                                                      | Why                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| A53 | A task can be for one group or for the **whole farm** (no group). Each farm has a Tasks page with Overdue, To do and Done sections. Tasks can be edited, and deleted after a confirmation; unlike treatments, tasks are working notes, not audit records.                       | Many jobs (troughs, fencing, machinery) aren't about one group.              |
| A54 | A task can **repeat** every 1–365 days. Ticking one off makes the next one at most once (unticking and ticking again doesn't make another). The next due date continues the original schedule, skipping dates already passed, so a late task doesn't come back already overdue. | Keeps a weekly job on the same weekday, and avoids a pile of overdue copies. |
| A55 | Assigning tasks to people waits for farm sharing (FR-8.2), since only the owner can see a farm today. In emails, a farm-wide overdue task is labelled "Whole farm".                                                                                                             | FR-5.4 needs other members first.                                            |
